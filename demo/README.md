# longluxi demo — 整本典籍·一次通读（混合：预设秒回 + 真模型实时）

投资人/客户演示页。**两种回答路径**：

- **预设题** → 客户端预置的真实结果，**秒回**、带完整出处/原文/命中卷轴（节奏可控，最稳）。
- **自由提问** → **实时调用真模型**（vLLM 2M reader，整本书驻留上下文），流式吐答案；
  出处、原文、命中位置卷轴**由后端在原文里现查现算**，所以「随便问、问新题也不露馅」。
- **四库全开（229 万 tok）** → 维持端到端检索叙事（>2M reader，是 10M 路线图，不实跑）。

## 跑起来（需要两个服务）

```bash
# 1) vLLM 2M reader（占卡 0–3，加载约 10 分钟）
MODEL=/home/user01/Minko/models/Qwen3.5-4B PORT=8001 TP=4 \
  MAX_LEN=2097152 GPU_MEM_UTIL=0.92 CUDA_VISIBLE_DEVICES=0,1,2,3 \
  bash eval/runners/vllm_server.sh > /tmp/vllm_demo.log 2>&1 &

# 2) demo 后端（同时托管页面 + 实时问答代理）
.venv/bin/python -m uvicorn demo.server:app --host 0.0.0.0 --port 8800 &

# 3) 浏览器打开
#    http://localhost:8800
```

页面加载时会探测 `/status`：vLLM 在线则右上角显示「● 实时在线」，自由提问走真模型；
否则自动降级为纯预设模式（也能放，只是自由提问会提示启动后端）。

> 数据准备（已完成，仅供重跑）：`.venv/bin/python demo/prepare_books.py`
> —— 从 `books_raw/`（Project Gutenberg 公版全本）抽正文、繁转简、用模型分词器实测 token 数，
> 产出 `books/*.txt` + `books/manifest.json`。

## 演示动线（建议）

1. 开场停在 **红楼梦**，顶部读数 `2,000,000 tokens · 0 切片 · 单针 100%`，下面一条实物锚点：
   `2M ≈ 红楼+三国+西游 三部一次通读`。
2. 先点一道**预设题**（秒回，展示完整「出处+原文+命中卷轴」三件套，朱砂印滑到全文 N% 处）。
3. **压轴杀招**：在输入框**当场随便敲一个没预设过的细节问题**（如"袭人原来叫什么名字"），
   看它实时通读全本、流式作答，并给出**现查的原文 + 回目 + 命中位置**。这一步直接回应
   "问新问题会不会露馅" —— 不会。
4. 切到 **四库全开**，当场问一个跨书问题（如"金箍棒多重"）——看它**分层检索命中《西游记》→ 通读该卷作答**。这是 10M 路线图的最小真实版，不再报"超长"。
5. 演示左下 **上传文档**：拖一个 **TXT/MD** 进去 → 建索引 → **左侧典籍库出现新卡片并自动进入新对话** → 当场对你自己的文档随便问（真模型作答）。

## ⚠️ 内部须知：真 vs 演（已随实时化更新）

| 元素 | 真实性 |
|---|---|
| **自由提问的答案 + 原文 + 回目 + 命中位置%** | ✅ **全部实时真跑**：真模型作答，引用片段与位置由后端在原文里现查现算 |
| 四大名著预设问答 | ✅ 真实可核对的名著事实，且只问"细节召回"——命中模型 100% 验证的检索能力 |
| 顶部读数（2M / 单针 100% / +45pp） | ✅ 来自 `docs/reports/`（NIAH 2M=100%、InfiniteBench 泄漏对照 +45pp）|
| 实物锚点 token 数（184 万 / 229 万） | ✅ 用模型分词器**实测**（见 `books/manifest.json`）|
| 首次提问的 1–2 分钟"通读"延迟 | ⚠️ 真实存在（全本 prefill）。选书时已**预热缓存**把它藏起来；之后同书提问 ~15–20s |
| 四库全开自由提问 | ✅ **真跑**：轻量路由（IDF 加权子串）在 4 本里选出命中卷 → 真模型通读该卷作答 + 现查出处。这是 10M「分层检索 → 2M reader」路线图的**最小真实版**（读单卷，非把 229 万一次塞进 reader）|
| 四库全开「229 万一次性塞进 reader」 | ⚠️ 不做（>2M）。完整 10M harness（BM25+dense+RAPTOR）仍是设计稿 |
| 上传 **TXT/MD** 后的真实问答 | ✅ **真跑**：`/register` 入库 → 同单本链路实时作答 + 命中定位 |
| 上传 **PDF/EPUB** 后的问答 | ⚠️ 仅"建索引"视觉 + 入库卡片；真实解析需后端接 PDF/EPUB 抽取（未做）|

**对外口径**：能力主张（2M 上下文、整本直读、单针 100%、+45pp、**自由提问实时可验证**）全部站得住、经得起尽调。
"10M / 229 万 / 分层检索"是**在建路线图**，按"我们的端到端方向"讲，别说成"已上线"。
**刻意只演细节召回、不演跨书推理**——后者是 base 模型的诚实弱区（RULER vt≈0、LongBench-v2≈0.25），现场问到会翻车。

## 关停 / 资源

```bash
# 停后端（按端口）
kill $(ss -ltnp | grep ':8800' | grep -oP 'pid=\K[0-9]+' | sort -u)
# 停 vLLM（释放卡 0–3）
kill $(ss -ltnp | grep ':8001' | grep -oP 'pid=\K[0-9]+' | sort -u)
```

vLLM 占用卡 0–3（硬规则，勿动 4–7）。单本书 ~45–68 万 token，稳稳落在 2M reader 内；
四本合计 229 万 token，正好越过 2M，这也是"分层检索 → 2M reader"叙事的现实依据。

## 文件

| 文件 | 作用 |
|---|---|
| `index.html` | 单文件前端（预设数据 + 实时 SSE 客户端）。`CORPUS` 对象含预设书目/问答 |
| `server.py` | FastAPI 后端：托管页面、`/ask` 实时流式、`/warmup` 预热、`/status` 探测；citation 在原文现查 |
| `prepare_books.py` | 数据准备：抽正文/繁转简/实测 token |
| `books/*.txt`, `books/manifest.json` | 清洗后的四大名著全本 + token 清单（后端运行所需）|
| `books_raw/` | Project Gutenberg 原始下载（gitignored，可删）|
